# 네트워크 공격 탐지 대회를 마치며

## 좋은 모델과 좋은 대회 모델은 같은가?

이번 대회 데이터에는 Timestamp가 포함되어 있었고, 공격 유형이 특정 시간대에
집중되는 특징이 있었다. 이 데이터에서 시간은 단순한 부가 정보가 아니라 공격 유형을
구분하는 강력한 변수였다.

처음에는 Timestamp를 모델에서 제외해야 한다고 생각했다. 모델이 시간대별 공격
패턴을 학습하면 실제 공격 행위가 아니라 공격이 발생한 시간을 외울 수 있기 때문이다.
학습 데이터에서 오후 3시에 발생한 Infilteration이 실제 환경에서는 새벽 2시에
발생한다면 시간에 의존한 모델은 탐지에 실패할 수 있다.

실제 IDS라면 패킷 크기와 개수, Flow 지속 시간, Forward·Backward 비율, TCP Flag,
포트, 트래픽 밀도와 전송 간격 같은 구조적인 행위를 학습해야 한다고 생각했다. 이
방향은 실제 환경에 일반화되는 IDS 관점에서는 합리적이었다.

## 내가 놓친 점

이번 과제의 일차 목표는 범용 IDS가 아니라 주어진 평가 분포에서 높은 점수를 얻는
것이었다. Public과 Private 데이터가 유사한 수집 구조를 따른다면 Timestamp는
제거해야 할 노이즈가 아니라 점수에 직접 영향을 주는 핵심 피처가 된다.

나는 아직 관찰되지 않은 상황을 너무 많이 고려했다.

- Private 데이터의 시간 분포가 완전히 달라지면 어떡하지?
- 다른 시간에 공격이 들어오면 어떡하지?
- 네트워크 환경이나 사용자 행동이 달라지면 어떡하지?
- 공격자가 전혀 다른 방식으로 접근하면 어떡하지?

이런 가능성을 고려하는 것은 중요하다. 하지만 확인할 수 없는 모든 상황을 동시에
대비하려 하면 현재 데이터가 제공하는 강력한 신호를 사용하지 못한다. 문제는 과적합을
경계한 것 자체가 아니라, 관찰되지 않은 가능성을 과도하게 상상하면서 현재 문제의
목적과 데이터 구조를 충분히 활용하지 못한 것이었다.

## 대회 모델과 실제 IDS

대회 점수가 목표라면 Timestamp를 포함한 모델과 제외한 모델을 모두 만들고, 시간
파생 변수도 검증해야 한다. 랜덤 분할만 사용하면 시간 패턴을 외운 효과를 실제
성능으로 착각할 수 있으므로 시간순 검증 결과도 함께 비교해야 한다.

실제 IDS가 목표라면 되도록 절대 Timestamp 의존도를 낮추고 최근 10초·60초 트래픽
밀도, 패킷 수, 포트 다양성과 같은 상대적인 시간 특성을 사용한다. 공격 Recall뿐
아니라 정상 오경보를 함께 평가하고, 머신러닝 뒤에 설명 가능한 규칙과 예외 처리를
결합한다. 운영 중 발생한 오탐은 Hard Negative로 다시 학습할 수 있다.

실제 시스템에서는 한 번의 예측으로 작업이 끝나지 않는다.

- 공격 여부 예측
- 규칙 기반 예외 처리
- 오탐과 미탐 분석
- 새로운 공격 패턴 반영
- 임계값 수정
- 모델 재학습
- 운영자 피드백
- 지속적인 유지보수

예측 성능과 대응 가능성 사이의 균형이 중요하다. 정확도가 조금 높은 복잡한 모델보다
경보 이유를 설명하고 빠르게 수정할 수 있는 모델이 더 유용할 수도 있다. 반대로
규칙에만 의존하면 새로운 공격을 놓칠 수 있으므로 머신러닝과 규칙을 함께 사용하는
방식이 적절하다.

## 최종 교훈

처음의 생각은 틀렸다기보다 목적이 달랐다. Timestamp를 제거하려 한 것은 실제
환경에서도 일반화되는 IDS를 위한 선택이었다. 하지만 이번 대회 점수를 위해서는
데이터가 가진 시간 구조를 활용하는 것이 더 적절할 수 있었다.

보이지 않는 모든 변수를 미리 해결하려 하지 않아도 된다. 대신 다음을 확인한다.

1. 데이터 누수가 없는지 확인한다.
2. 랜덤 분할과 시간순 분할 결과를 비교한다.
3. 특정 변수 하나에 성능이 과도하게 의존하는지 확인한다.
4. Public과 Private 분포 차이를 위험 요소로 기록한다.
5. 검증 결과가 좋은 모델을 우선 선택한다.

상상만으로 변수를 제거하기보다 실험으로 포함 여부를 결정했어야 했다.

> 좋은 피처는 절대적으로 정해져 있지 않다. 모델의 목적과 배포 환경에 따라 달라진다.

> 확인되지 않은 미래를 지나치게 상상하기보다 검증 가능한 위험부터 관리해야 한다.

좋은 모델링은 모든 가능성을 한 번에 해결하는 일이 아니다. 문제의 목표를 명확히
정하고, 데이터에서 확인되는 사실과 아직 확인되지 않은 가정을 구분한 뒤, 실험
결과에 따라 하나씩 판단하는 과정이다.
